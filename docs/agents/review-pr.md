# Following a pull request

Reach for this on every pull request you open or update, a stack level included. It catches what a change breaks before it merges; the whole-codebase recheck in [review-codebase.md](review-codebase.md) catches what no single change shows. That page also says what each review skill is for and which habits keep the agents safe.

1. **Gate before opening.** The change has its red test first (`mattpocock-skills:tdd`), and `uv run pre-commit run --all-files` passes, read to the end (`caveman:verify-and-stop` runs the gates and stops at the result). Run `simplify` and `ponytail:ponytail-review` on the diff. A restructure goes through `caveman:safe-refactor`, a change of the protocol or of the saved variables through `caveman:migration`: an older peer and an older saved file still work.
2. **Add the lens the change needs.** `security-review` when the change reads what other players send (`Protocol`, `Sync`, `CHAT_MSG_ADDON`), changes what Mnemosyne sends, or touches the saved variables or the debug report ([wow-api.md](wow-api.md)). A change to `Client` or `Interface` says in its description what was checked in the game ([testing.md](testing.md)). A change players see updates README.md ([AGENTS.md](../../AGENTS.md)).
3. **Open it**, assigned, and stacked as AGENTS.md says, with the body written by `mattpocock-skills:pr`.
4. **Read the diff again with fresh eyes.** Run `code-review` on the pull request number, and `mattpocock-skills:code-review` with the pull request's base as the fixed point and its description as the spec. In a stack, review the levels bottom to top. Brief each reviewer as in step 2 of review-codebase.md: graphify first, its commands listed in the report.
5. **Verify each finding** before touching code, as in review-codebase.md. Fix the verified ones in the pull request they belong to: amend its branch, update its description, rebase the levels above it, `git push --force-with-lease`.
6. **Wait for CI.** Every required check passes before the work counts as done. When one fails, read its log (`gh run view <id> --log-failed`) and diagnose before editing: `mattpocock-skills:diagnosing-bugs` for a failure you can reproduce, `caveman:investigate-first` when the cause is unclear or the failure shows only on CI. Fix it in the same pull request. A failure that is not this change's own gets its own pull request, at the bottom of the stack if the levels above need it.
7. **Watch the merge.** After the squash lands, open the runs it triggered on `main` (Release, Cache warm). A red one is a finding: diagnose it as in step 6, and fix it in a new pull request.

The pull request is done when the required checks are green, no verified finding is open on its diff, README.md matches what players will see, and its description matches what the change does.
